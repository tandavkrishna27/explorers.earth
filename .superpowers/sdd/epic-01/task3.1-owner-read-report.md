## Contract and authorization

- New owner GET `/api/explorers/v1/collections` requires category and accepts only status (`active` default or `archived`), limit (24 default, 1..100) and cursor. GET `/recommendations` also accepts an optional owned active collectionId. It returns category-wide recommendations when collectionId is absent. GET `/collections/:id` and `/recommendations/:id` accept only status, default active. Explicit archived detail/list selection is available; there is no implicit mixed active/archive listing. An archived parent is not a valid child-page filter; its surviving recommendations remain available to the owner through category/detail reads, with archived memberships explicitly labelled.
- Owner transport uses existing `requireActor`, then `OwnerContentService` independently calls `authorizeOperation` for `collections:read` or `recommendations:read` before input/resource handling, within the repeatable-read snapshot, and again in a fresh database snapshot after COMMIT before delivery. Current membership, owner role, lifecycle, security/session generation, session existence/expiry, and OAuth named scopes are rechecked. OAuth tests pass trusted Actors through the internal service; no OAuth credential resolver/transport/grant-verification capability is added or claimed.
- Every content, membership, media and pin query is scoped to Actor.accountId; detail/parent queries include owner/category predicates without a preceding foreign private lookup. Caller accountId/userId/header credentials and unknown query keys fail closed. Foreign and missing detail responses use the same404 message; malformed inputs422, stale continuation409, absent/expired session401, inactive account403. Every GET response, including errors, is no-store.
- `explorersOwnerContentContract.ts` exports browser-safe Zod validators and types. Owner collection core extends the existing core with archived and displayOrder. Recommendation core adds every owned collection membership (collectionId, collectionRevision, displayOrder, archived) and the selected category pin when present (collectionId, position, category pin revision). No rich notes/provider facts/display overrides/receipt data/raw storage keys are serialized. This is explicitly a partial core interface, not the complete category/editor DTO or top-pick mutation contract.

## Pagination and complete-set behavior

- Bounded response item pages use limit+1 keyset reads, deterministic `(display_order,id)` for collections and selected-collection children, or stable ID order for category-wide recommendations (constant order component). There is no OFFSET or nested first-page child array presented as a complete aggregate.
- AES-256-GCM authenticated encrypted continuation tokens use a domain-separated key derived from canonical server config. They bind account, operation, category, status, selected collection, order/version and limit. Tokens contain a category snapshot fingerprint and an absolute ten-minute expiry carried forward across pages. Tamper, rebinding, expiry or secret rotation returns422 and requires a restart. They carry no plaintext private account/membership context.
- Each page has one repeatable-read read-only snapshot. A SHA256 fingerprint computed entirely in PostgreSQL covers category collections, recommendations, membership rows, typed media relations, category pins and pin revision; the database returns only the fixed-size fingerprint, not the raw aggregate. A changed category fingerprint returns409, detecting membership changes even if a maintenance operation did not bump collection revision. Other changes in the same category conservatively invalidate a cursor too. Supported stale writes still require the existing expectedRevision and exact-member-set server checks; a client completion marker never replaces those checks.
- The existing `explorersApiClient` now exposes typed list/detail methods plus sequential `getAllMyCollections` and `getAllMyRecommendations`. Complete readers reject schema/context/filter mismatches, changed snapshots, duplicate IDs, empty continued pages, repeated cursors and more than1000 pages. They never return partial success after a later-page failure. Retrying calls starts at page one; errors propagate for consumer retry state.
- Reads capture canonical account/session generation, subscribe to store changes and abort in-flight fetches on account/generation/logout changes. They check authority again after response parsing and before returning completion. External AbortSignal is honored and listeners are removed. Existing definitive401 behavior is retained without logging out a newer generation.
- Only the sequential collector creates a frozen result/items array registered in a private WeakSet. `assertCompleteOwnerContent` rejects first-page objects, forged completion shapes and completed sets from an older account/generation. Future aggregate managers must call this before saving and supply observed server revisions. Existing legacy category managers are not switched to this API in this slice; their UI retry rendering and aggregate integration remain open. No complete-set writer or top-pick write was added.
