## Result and writer prerequisites

The existing frontend `explorersApiClient` now exposes `getCompleteMyCategoryContent({category,status}, signal)`. It obtains one v2 category snapshot, collects sequential collection, recommendation and membership pages using exactly that token/revision/absolute expiry, joins every membership and pin, and invokes the server snapshot-validation endpoint after the last data page. Only then does it return a deeply frozen DTO with the category revision, pin revision, account and captured session generation, registered in a private WeakSet.

`assertCompleteMyCategoryContent` rejects fabricated/copied DTOs, pages, actual individual-collector results, expired snapshots and changed account/session generations. The existing individual compatibility collectors retain their own resource-only authority and cannot grant category-wide eligibility. `copyMyCategoryContentForStaging` explicitly copies all mutable rows, media arrays and pin objects; its draft has no completion authority. Future consumers must preserve the original complete observation separately and call its assertion immediately before staging/saving.

Final server validation closes the race between data reads and completion. It is **not a write lock**. A future category/top-pick writer must take the approved account/category locks and compare this expected category revision inside its own transaction, alongside applicable aggregate/pin revisions and command receipt semantics. No writer or UI flow is introduced here.

## Rulings and finite bounds

Ruling: `status` selects recommendation state; the collection stream always uses `all`, and memberships use `collectionStatus=all` plus the requested recommendation status. This includes every required archived parent while preventing intentionally filtered recommendations from becoming false missing joins. The returned collection array therefore contains all parent states; future consumer presentation must select its desired visible collection status explicitly. Tests exercise active children with archived parents and archived/all recommendation feeds.

Ruling: use 24 items per sequential page, one shared maximum of 1,000 HTTP requests including initial snapshot/final validation, and 100,000 rows per stream. The request bound is currently stronger than the row bound: at most 998 data pages × 24 rows can complete across all streams. The explicit row guard remains a separate defense if paging changes. No injectable production budget/test bypass was added; the actual shared request bound is tested to rejection.

Ruling: each response has a 4 MiB actual streamed UTF-8 byte bound matching checkpoint B; cumulative response bytes are capped at 64 MiB. The cumulative guard bounds payload accumulation independently of the potentially multi-gigabyte 1,000 × 4 MiB theoretical transport ceiling. This is a client transport/memory safeguard, not a new domain cap or an exact process-heap ceiling (parsed objects/strings have overhead). It can reject a legally stored large category; it returns a typed failure without any partial result/marker. The 17th individually legal near-4-MiB page demonstrates cumulative rejection. Declared length can reject early, but actual streamed chunks are always counted; missing/lying headers cannot disable the byte guard. Oversized streams are cancelled before JSON parsing. No silent clipping, per-item fanout or automatic restart loop is used.

Malformed data, mismatched snapshot/revision/expiry, duplicate DTO IDs/tuples, reused cross-stream/repeated cursors, continued-empty pages, missing joins, incompatible archive states, wrong parent/pin revision, duplicate pin positions and missing/archived pin targets fail with typed `ExplorersApiError`. API failures preserve their status/code; transport failures become typed `UNAVAILABLE`; cancellation becomes typed `ABORTED` with `AbortError` name. Definitive 401 expires only the current generation even with a malformed body. Auth-store subscription spans the whole joint operation, and A→B→A fails even when account IDs become equal again.
