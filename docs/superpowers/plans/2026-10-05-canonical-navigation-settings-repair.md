## Evidence and root cause

Canonical `store.ts:73–78` intentionally stores `user.id` as auth identity and `user.documentId` as account UUID; `accountId` is explicit. `CategoryNavigationProvider.tsx:66–70` passes documentId to `categoryNavigationApi.ts:8–16,59–64`, which queries usersPermissionsUser→accounts. Its commit still writes updateAccount and eligibility still uses CHECK_PUBLISHED_LISTS. Settings independently issues SettingsAccount and getPublicCategoryListCountsQuery (`Settings.tsx:36–49,146–155,262–271`). main.tsx strips canonical credentials from Apollo and omits cookies; inspected canonical composition has no GraphQL registration. This source-proven producer/consumer mismatch agrees with saved exact-dc61 Category A/B/Publishing wrong-subject first errors; exact current request variables and deployed proxy behavior are not newly observed.

Working replacement: `AccountDto` contains id, status, revision, autoPinning and nine `categories[{category,isPublic,displayOrder,pinnedOrder}]`; `ProfileService.getMyProfile(actor): Promise<AccountDto>` and `updateAccount(actor,input: UpdateAccountInput & RevisionInput,context: RequestContext): Promise<AccountDto>` authorize canonical membership. `explorersApiClient.getMyProfile(signal?: AbortSignal)` and `updateAccount(input,signal?)` use cookie HTTP. Repository requires the full nine-category set and performs optimistic revision checking. Do not add a second settings database or route.
