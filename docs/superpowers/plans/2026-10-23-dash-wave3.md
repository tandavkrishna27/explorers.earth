**Architecture:** On `origin/main` a guide is a `collections` row plus `guide_collection_details` and ordered `guide_sections` (0050); **a day is one `guide_sections` row** (`display_order` = day index, the SPA shows `displayOrder + 1`), and the morning/afternoon/evening slots live inside `blocks` JSON (`blocks.timeline.{morning,afternoon,evening}`), guarded by a deferred trigger that scans `$.**.photos[*].mediaId`. So 0069 does NOT add a table: it introduces block version `guide-section-blocks/v2` where `blocks.items` is the day's single ordered list (array index = position, `timeLabel` nullable on each item) and `blocks.budget` becomes `{entries}`; the migration rewrites every v1 row in SQL. Every day/item command is one transaction under the existing guide revision lock (`lockGuideAtRevision`), so a cross-day move is atomic. Legacy readers (public guide views, old modals) keep working through shared adapters `legacyTimelineFromItems` / `mergeLegacyTimeline`. 0070 adds `collection_list_links` and copies `collection_location_links` into it (old table kept until a later cleanup). 0071 adds `is_sample` with CHECKs that make a sample unpublishable in storage, plus permanent seeding receipts.

export function normalizeTimeLabel(raw:string):GuideTimeLabel|null{
