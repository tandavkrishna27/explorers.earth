# CI optimization plan (proposal only)

Source inventory: nine `.github/workflows/*.yml` files on `codex/unified-replatform`; timing sample: green PR runs at `c64a274e9b62b35e4444f7e988cee781ddb37911` on 2026-09-30. No workflow, setting, or test change was made for this plan. The goal is a 10–15 minute **PR validation wall time** without dropping checks; the current sample does not prove that goal is reachable on every hosted run.

E2E's four commands passed 45 category-navigation tests in 13.8m, 11 public-shell Chromium tests in 6.8m, 69 music-publishing tests in 6.4m, and 75 Music/accessibility/account tests across `chromium-pr-safe`, `firefox-music-visual`, `webkit-music-visual` in 5.2m ([job log](https://github.com/tandavkrishna27/explorers.earth/actions/runs/36724334669/job/109919494352)). The 45-test category suite is one file with `workers: 1`, `retries: 0` and no `fullyParallel`; ordinary file-level sharding would put that whole file on one shard. Test count is not a proxy for duration. The final default-config command has CI retries 2; preserve this, while the first three configs retain their own retry settings. The Music workflow's browser command explicitly uses `--retries=0`; preserve its separate evidence.

Node/setup caches already exist, but each Music job performs a fresh checkout and `npm ci` (typically 7–19s here). Those repeated installs add runner minutes; they are not the 16-minute wall-time cause. Playwright installation costs ~2m15–2m18s in each browser runner. Sharing mutable `node_modules`, browser processes, fixtures or a PostgreSQL service across jobs would add authority and contamination risk; do not make that the first optimization.

## Stages and trust-preserving changes

1. **Freeze the authority contract and measure a second head.** Keep the two main required checks `replatform-required` and `music-required` (strict, GitHub Actions-bound) and current workflow paths. `tunes.yml` release preflight explicitly accepts only successful **main push** runs of `.github/workflows/ci.yml`/`replatform-required` and `.github/workflows/test.yml`/`music-required` at exact `GITHUB_SHA`. No workflow-file or aggregate-job rename can precede a coordinated preflight/test/protection migration. Record per-job step times and Playwright JSON counts on a second clean hosted SHA; do not treat a cached or skipped job as a speed win. The known 142-diagnostic Tunes type baseline remains a regression comparator, never a green full typecheck claim.
2. **Two contained E2E jobs and Music dependency proof.** Replace `e2e-tests` with `e2e-category-navigation` running the exact 45-test category command and `e2e-public-music` running the other three exact commands in their current order (155 tests). Preserve both jobs' current `needs: [lint, typecheck, unit-tests]` first, PR-safe environment, browser/project flags, per-config retries, and 45-minute timeout until hosted variance is known. Use unique report/failure artifact names and unchanged contents. Add both IDs to `replatform-required.needs`; its `always()` predicate must reject either failed, cancelled or skipped job. Measured test loads are 13.8m versus 18.4m; with duplicated setup, estimate ~21–22m from E2E start and ~26m total CI, **not** 2×. In parallel, inspect Music job outputs: the chain currently has separate checkouts and no apparent shared artifact; only remove `needs` edges after workflow-contract proof that each can run independently on an isolated runner. Keep all ten required Music jobs in `music-required`. For PR/main push, `image-deploy-contract` can run independently if it retains full tests; for nightly, explicitly require successful `load-chaos` in the aggregate when selected, preserving the present indirect failure behavior. `load-chaos` stays optional only for ordinary PR/push. This could move Music's ~16.5m path toward its 7.5m browser lane, subject to runner contention.
3. **Four/five E2E runners only after category isolation.** A four-job layout still has a likely ~11.6–13.2m paired-suite runner plus ~3m setup, so it may miss 15m after scheduling. For a credible 10–15m target, split the single category spec into two independently runnable, time-balanced files/groups with the same test titles/assertions/fixtures and retain `workers: 1` inside each. Then use five jobs: category A, category B, public shell Chromium, music publishing, and the current three-project Music/accessibility/account command. Each should have a distinct artifact/report path; no shared fixed port exists across isolated runners. Category's 13.8m divided near evenly plus ~3m setup yields a tentative ~10–12m E2E completion **if** jobs start near workflow launch. Removing artificial lint/type/unit prerequisites may cut another ~5m because E2E consumes no outputs from those jobs, but increases wasted compute on early failures. The strict aggregate still requires every lane; no check becomes optional. Prove suite-level state isolation first—do not merely add `fullyParallel` or `--shard` to one file and assume balanced, equivalent tests. Keep 45-minute timeouts until benchmark evidence supports smaller values.
4. **Trigger/billing cleanup and names as separate migrations.** The same SHA ran [push CI 36724327667](https://github.com/tandavkrishna27/explorers.earth/actions/runs/36724327667) and PR CI 36724334669; `ci.yml` groups by `github.ref`, so branch push and PR refs do not cancel one another. Music concurrency also includes event name; C0/Tunes likewise trigger both events. Once PR-based branch validation is established, consider removing only integration-branch push triggers from the four validation workflows while retaining all main push runs for release preflight and PR runs for merge protection; document the loss of pre-PR branch feedback and verify no release path consumes an integration push run. Alternatively keep both and budget the duplicate cost. Clean display names only after dashboards/contracts are updated. Preserve protected aggregate job names and workflow paths unless branch protection, exact-SHA release preflight, dependent contracts and hosted readback are migrated together; never use a temporary required-check gap.

## Parity and stop rules

Before editing, save a manifest of the four exact CI Playwright commands/configs/spec/project flags and their 45/11/69/75 counts; Music's static/scoped+142-baseline, critical coverage, full contracts, seven real-PG files, security, frontend, three-project browser, image/deploy/real-Traefik contracts, repeatable fixture seed/routes; C0 Ubuntu/Windows plain installs/contracts; Tunes full test/integration/coverage/types, exact image build/smoke, fixable-high fail gate and full SARIF. Compare test lists and hosted reports after each stage. Required jobs must all conclude `success` on the **same head SHA**, with no added skip or weaker retry/coverage threshold; preserve optional nightly qualifications and all PR read-only token/secret boundaries. Run workflow authority/security tests, YAML/actionlint, local Playwright `--list` parity, then exact-SHA hosted PR and main-push proofs before changing protection or release trust. A failed/absent artifact, unbalanced category partition, new flaky test, or skipped required lane stops rollout and reverts that stage.

The optimistic five-job floor is roughly 10–12m E2E plus scheduling; image qualification remains ~8m and Music could be ~8m after dependency flattening. A 10–15m **overall** PR gate is plausible only with the later category split, early E2E starts, enough concurrent runners, and stable hosted timings. Two-job E2E alone cannot reach it. Five E2E runners repeat ~3m setup each: from this sample, total E2E billed time may rise from ~35 to roughly 47 runner-minutes per event, and duplicate push/PR events can double that. Measure wall time and billed minutes on at least two hosted heads before promising the target or narrowing timeouts; cache/browser download variance, retries, Docker/registry latency and runner availability can keep the actual gate above 15m.
