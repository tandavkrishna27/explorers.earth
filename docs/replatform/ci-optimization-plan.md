# CI optimization plan (proposal only)

Source inventory: nine `.github/workflows/*.yml` files on `codex/unified-replatform`; timing sample: green PR runs at `c64a274e9b62b35e4444f7e988cee781ddb37911` on 2026-09-30. No workflow, setting, or test change was made for this plan. The goal is a 10–15 minute **PR validation wall time** without dropping checks; the current sample does not prove that goal is reachable on every hosted run.

## 2026-10-18 update: merge-train cost

`main` requires `replatform-required` and `music-required` with `strict: true` (classic branch protection, GitHub Actions app 15368), so every merge forces every other open PR to update from `main` and re-run all of CI. A cycle is about 20 minutes; Backend validation, Explorers validation, API image validation and Music C0 contracts all run for 10-20 minutes. A train of six PRs took about two hours. Three changes address that without weakening a required gate: a flaky E2E case is fixed at its root, docs-only PRs skip the lanes that cannot see Markdown, and the merge-queue option is assessed below (recommendation only; no repository setting was changed).

### 1. The `Manual explicit Pin` flake: fixed at the root

**Symptom.** `e2e/category-navigation-a.spec.ts` › `<category>: Auto saved → header Off → reload → Hub On → Manual explicit Pin` timed out after 12000 ms in `locator.press` (`enable.press('Enter')` at line 503 or `pinAction.press('Enter')` at line 509). Three hosted runs I could retrieve failed this way on unrelated PRs, one of them the docs-only PR #137: [39136378756](https://github.com/tandavkrishna27/explorers.earth/actions/runs/39136378756) (apps, line 509), [39134397260](https://github.com/tandavkrishna27/explorers.earth/actions/runs/39134397260) (books, line 509) and [39129584129](https://github.com/tandavkrishna27/explorers.earth/actions/runs/39129584129) (books, line 503). A fourth failure in the same file, [39129246940](https://github.com/tandavkrishna27/explorers.earth/actions/runs/39129246940), was a different test on an older commit. The case moves between categories, so it is not specific to one.

**What the CI traces show.** In every failure the call log reads: locator resolved to the menu button, `elementHandle.press("Enter")`, `element was detached from the DOM, retrying`, and then nothing. In run 39134397260 (trace time) the Category options click landed at 320.391 s (after waiting 3.6 s for the full-screen Earth loader to stop intercepting the pointer), the menu was in the DOM at 320.427 s, the press resolved the button at 320.661 s and the button was detached at 320.698 s. The menu never came back, so Playwright spent the remaining 12 s retrying a button that no longer existed. It was not a slow press, a focus race or a pending write; the menu closed itself.

**Root cause.** `RecommendationCard` in `explorers-earth/src/pages/RecommendationsHub.tsx` closed the portaled kebab menu on **any** `scroll` event, via a capture-phase listener on `window`. The hub sits inside the layout's `overflow-auto` scroller, which is always scrollable by about 54 px (`min-h-screen` plus the header padding). Whenever content above the grid appears or disappears (`Verifying your account…`, `Saving category settings…`, the route loader) the scroller's `scrollTop` is clamped or re-anchored and the browser fires a `scroll` event nobody asked for. Instrumented local runs (6x CPU throttle, to imitate a hosted runner) logged that sequence: the scroller's `scrollTop` goes 54 → 16 → 12 → 0 in several `scroll` events within about 1.5 s of load while the Earth loader and the verifying banner leave, and again when the saving banner appears. Any click that lands in one of those windows loses its menu; hosted runners hit the window, an idle laptop mostly does not (40 of 40 passes before the fix). The same defect is user-visible: open a category menu while a status line above the grid goes away and the menu vanishes under the pointer.

**Deterministic reproduction.** Open the menu, then set the layout scroller's `scrollTop` once. Before the fix the menu is removed every time; after it, it stays (probe run during diagnosis, not committed: `e2e/zz-diag-scroll.spec.ts`, fail → pass). Component-level regression tests in `src/pages/__tests__/RecommendationsHub.navigation.test.tsx` pin the same behaviour; two of the four fail against the old component.

**Fix (app, not test).** The menu now follows its trigger instead of closing: scroll and resize reschedule one `requestAnimationFrame` that re-measures the trigger and re-anchors the menu, and the menu closes only on an outside press, on an item choice, or when the trigger itself has scrolled out of the viewport. No timeout was raised and no retry was added. One behaviour change to be aware of: while the page scrolls, an open menu now tracks its button rather than closing. Revert `RecommendationsHub.tsx` to restore the old behaviour; the regression tests would then fail, which is intended.

**Evidence.** See the PR description for the consecutive local pass counts (books and games, the full spec case, `--repeat-each=20`) and the throttled stress run. The earlier unthrottled baseline of 40 consecutive passes before the fix shows why the flake needed a loaded runner to appear.

### 2. Docs-only pull requests skip the lanes that cannot see Markdown

Each of `ci.yml` and `test.yml` gained a `changes` job. A pull request is **docs-only** when every changed path is Markdown (`*.md` or `*.mdx`) and the workflow ran on a `pull_request` event on the two-parent merge commit GitHub builds. `scripts/ci-docs-only.cjs` decides and fails closed: every other event (push, schedule, manual), a missing merge commit, an empty diff, a git error and any non-Markdown path all answer `docs_only=false`, which runs everything exactly as before. Renames are diffed with `--no-renames`, so code cannot hide behind a `.md` name.

"Markdown" is deliberately narrower than `docs/**`. `docs/` also holds JSON, SQL, `.cjs`, `.ts` and HTML that contract tests and the image build read (the runtime surface inventory is an image input), so those still count as code and still run every lane.

| Workflow | Docs-only PR | Everything else |
|---|---|---|
| `ci.yml` (`replatform-required`) | Every lane skips; the aggregate runs, depends on every job and passes only if each lane succeeded or was skipped because `changes` succeeded and said docs-only | Unchanged: every lane must be `success` |
| `test.yml` (`music-required`) | `static`, `unit-coverage`, `database`, `security`, `frontend`, `browser`, `image-deploy-contract` and `platform-fixture` skip. **`docs-contracts` and `contracts` never skip**: they read docs/, READMEs and CLAUDE.md (`music-documentation-contract` and friends) and are what keeps documentation honest | Unchanged |
| `music-c0-contracts.yml`, `tunes.yml` | Not triggered: Markdown is excluded as the last `paths` pattern (last match wins). They are not required checks | Unchanged, including non-Markdown files under `docs/` |

The required check names, workflow paths and aggregate job names are unchanged, so branch protection, the exact-SHA release preflight in `tunes.yml` and `ci-check-map.md` still hold. Push runs on `main` are never docs-only, so release preflight still sees full validation at its exact source SHA. If `changes` fails or is cancelled, every dependent lane skips, `changes` is not `success`, and both aggregates fail, so a broken classifier cannot turn into a free pass. The contract tests (`replatform-workflow-authority.test.ts`, `music-documentation-contract.test.ts`, `scripts/ci-docs-only.test.cjs`) run the real aggregate scripts from the YAML across every event and outcome combination.

**Before and after for a docs-only PR.** Before, measured on PR #137 (four Markdown files under `docs/superpowers/plans/`), per head SHA, wall clock of the slowest of the three workflows that ran (Explorers validation, Backend validation, Music C0 contracts): 21.9 min / 23.1 min / 17.8 min on the first head, 16.5 / 12.7 / 18.3 on the second, 9.5 / 8.5 / 20.5 on the third and 10.0 / 7.4 / 18.3 on the fourth (the C0 run, which `docs/**` triggered, was the critical path on three of four). After: C0 and image validation do not run, `ci.yml` is the `changes` job plus the aggregate (about 30 s), and `test.yml` is bounded by `contracts` at 212-251 s in the last three green runs plus the classifier and aggregate. Expected wall clock is about 4-5 min, a reduction of roughly 75-80 % against the 18-23 min median, and runner minutes fall from about 87 for the two required workflows alone (about 55 for `ci.yml` plus about 32 for `test.yml`, before counting the C0 matrix) to about 6. The after figure is derived from recorded job durations; the first docs-only PR after this merges gives the hosted measurement.

### 3. GitHub merge queue: assessment and recommendation (nothing changed)

**Verdict.** A merge queue is the right structural fix for the strict update-and-re-run loop, but it is **not available on this repository today**. GitHub documents merge queues for public repositories owned by an organization (or private ones on Enterprise Cloud). `tandavkrishna27/explorers.earth` reports `owner.type: User`; the `MeteoriteLabs/explorers.earth` remote redirects to it, so it was transferred from the organization at some point. I did not change any repository setting, so I could not confirm in the UI that the "Require merge queue" rule is absent, but the documented eligibility rule excludes it.

**What it would fix.** With `strict: true`, K PRs ready at once can cost up to K(K+1)/2 full CI cycles, because each merge invalidates the other K-1. A queue builds a temporary branch per entry (`gh-readonly-queue/main/pr-N-…`) containing the PR on top of `main` plus the PRs ahead of it, runs the required checks once on that, and merges. Entries are validated speculatively in parallel, so the six-PR train would take about one cycle plus queue overhead (roughly 25-30 min) instead of about two hours, and nobody updates branches by hand. The "up to date with main" rule is replaced by "the exact merge result passed".

**If the repository moves to an organization, the workflow edits are:**

1. Add `merge_group: { types: [checks_requested] }` to `ci.yml` and `test.yml`. Without it the required checks never report on the queue branch and every queued PR stalls. Do not add it to `music-c0-contracts.yml` or `tunes.yml`: `paths` filters are ignored for `merge_group`, so they would run on every entry for no gate.
2. Make `cancel-in-progress` false for `merge_group` in both `concurrency` blocks (`${{ github.event_name != 'merge_group' }}`). A cancelled queue run is a failed check and ejects the PR.
3. Extend `scripts/ci-docs-only.cjs` to read `github.event.merge_group.base_sha`..`head_sha` for `merge_group` (it returns `false` today, which is safe but would send docs-only PRs through full CI at queue time). A group is docs-only only if the whole group is Markdown. Needs `fetch-depth: 0` or an explicit fetch of `base_sha`, and the aggregates' `docsOnly` predicate must accept `merge_group` as well as `pull_request`.
4. Keep the `push` triggers on `main`: `tunes.yml` release preflight still requires a successful push run of `ci.yml` and `test.yml` at the exact source SHA. Note that squash or rebase queue merges create a new commit, so that run is a new full run, not the queue's.
5. Update `replatform-workflow-authority.test.ts` and the `music-documentation-contract.test.ts` workflow assertions that pin the `on:` shapes, and extend the aggregate matrices with `merge_group`.
6. Settings (owner action, not in code): replace the classic rule with a ruleset that requires `replatform-required` and `music-required` (GitHub Actions app 15368), requires a merge queue (merge method, max group size, a status-check timeout above the 45 minutes the E2E lanes are allowed) and drops `strict`. Keep PR-level runs for early feedback; they no longer need to be current with `main`.

**Costs and risks.** Every queued entry pays a full required run (about 55 runner-minutes for `ci.yml`, about 30 for `test.yml`), in parallel; a failure ejects the entry and re-runs those behind it; the repository move changes the Actions billing owner and URLs, and the GHCR mirror path `ghcr.io/tandavkrishna27/mirror/…` pinned in `test.yml` and the image build would have to move with it.

**Until then.** Options that exist today, in order of effect: (a) owner decision to set `strict: false`, relying on the `main` push run to catch semantic conflicts and revert quickly; (b) merge related PRs as one train PR instead of six; (c) keep shortening the ~19-minute lanes (they are not required checks, but they delay reviewers' attention).

## Stages and trust-preserving changes

1. **Freeze the authority contract and measure a second head.** Keep the two main required checks `replatform-required` and `music-required` (strict, GitHub Actions-bound) and current workflow paths. `tunes.yml` release preflight explicitly accepts only successful **main push** runs of `.github/workflows/ci.yml`/`replatform-required` and `.github/workflows/test.yml`/`music-required` at exact `GITHUB_SHA`. No workflow-file or aggregate-job rename can precede a coordinated preflight/test/protection migration. Record per-job step times and Playwright JSON counts on a second clean hosted SHA; do not treat a cached or skipped job as a speed win. The known 142-diagnostic Tunes type baseline remains a regression comparator, never a green full typecheck claim.
2. **Two contained E2E jobs and Music dependency proof.** Replace `e2e-tests` with `e2e-category-navigation` running the exact 45-test category command and `e2e-public-music` running the other three exact commands in their current order (155 tests). Preserve both jobs' current `needs: [lint, typecheck, unit-tests]` first, PR-safe environment, browser/project flags, per-config retries, and 45-minute timeout until hosted variance is known. Use unique report/failure artifact names and unchanged contents. Add both IDs to `replatform-required.needs`; its `always()` predicate must reject either failed, cancelled or skipped job. Measured test loads are 13.8m versus 18.4m; with duplicated setup, estimate ~21–22m from E2E start and ~26m total CI, **not** 2×. In parallel, inspect Music job outputs: the chain currently has separate checkouts and no apparent shared artifact; only remove `needs` edges after workflow-contract proof that each can run independently on an isolated runner. Keep all ten required Music jobs in `music-required`. For PR/main push, `image-deploy-contract` can run independently if it retains full tests; for nightly, explicitly require successful `load-chaos` in the aggregate when selected, preserving the present indirect failure behavior. `load-chaos` stays optional only for ordinary PR/push. This could move Music's ~16.5m path toward its 7.5m browser lane, subject to runner contention.
3. **Four/five E2E runners only after category isolation.** A four-job layout still has a likely ~11.6–13.2m paired-suite runner plus ~3m setup, so it may miss 15m after scheduling. For a credible 10–15m target, split the single category spec into two independently runnable, time-balanced files/groups with the same test titles/assertions/fixtures and retain `workers: 1` inside each. Then use five jobs: category A, category B, public shell Chromium, music publishing, and the current three-project Music/accessibility/account command. Each should have a distinct artifact/report path; no shared fixed port exists across isolated runners. Category's 13.8m divided near evenly plus ~3m setup yields a tentative ~10–12m E2E completion **if** jobs start near workflow launch. Removing artificial lint/type/unit prerequisites may cut another ~5m because E2E consumes no outputs from those jobs, but increases wasted compute on early failures. The strict aggregate still requires every lane; no check becomes optional. Prove suite-level state isolation first—do not merely add `fullyParallel` or `--shard` to one file and assume balanced, equivalent tests. Keep 45-minute timeouts until benchmark evidence supports smaller values.
4. **Trigger/billing cleanup and names as separate migrations.** The same SHA ran [push CI 36724327667](https://github.com/tandavkrishna27/explorers.earth/actions/runs/36724327667) and PR CI 36724334669; `ci.yml` groups by `github.ref`, so branch push and PR refs do not cancel one another. Music concurrency also includes event name; C0/Tunes likewise trigger both events. Once PR-based branch validation is established, consider removing only integration-branch push triggers from the four validation workflows while retaining all main push runs for release preflight and PR runs for merge protection; document the loss of pre-PR branch feedback and verify no release path consumes an integration push run. Alternatively keep both and budget the duplicate cost. Clean display names only after dashboards/contracts are updated. Preserve protected aggregate job names and workflow paths unless branch protection, exact-SHA release preflight, dependent contracts and hosted readback are migrated together; never use a temporary required-check gap.

## Parity and stop rules

Before editing, save a manifest of the four exact CI Playwright commands/configs/spec/project flags and their 45/11/69/75 counts; Music's static/scoped+142-baseline, critical coverage, full contracts, seven real-PG files, security, frontend, three-project browser, image/deploy/real-Traefik contracts, repeatable fixture seed/routes; C0 Ubuntu/Windows plain installs/contracts; Tunes full test/integration/coverage/types, exact image build/smoke, fixable-high fail gate and full SARIF. Compare test lists and hosted reports after each stage. Required jobs must all conclude `success` on the **same head SHA**, with no added skip or weaker retry/coverage threshold; preserve optional nightly qualifications and all PR read-only token/secret boundaries. Run workflow authority/security tests, YAML/actionlint, local Playwright `--list` parity, then exact-SHA hosted PR and main-push proofs before changing protection or release trust. A failed/absent artifact, unbalanced category partition, new flaky test, or skipped required lane stops rollout and reverts that stage.

The optimistic five-job floor is roughly 10–12m E2E plus scheduling; image qualification remains ~8m and Music could be ~8m after dependency flattening. A 10–15m **overall** PR gate is plausible only with the later category split, early E2E starts, enough concurrent runners, and stable hosted timings. Two-job E2E alone cannot reach it. Five E2E runners repeat ~3m setup each: from this sample, total E2E billed time may rise from ~35 to roughly 47 runner-minutes per event, and duplicate push/PR events can double that. Measure wall time and billed minutes on at least two hosted heads before promising the target or narrowing timeouts; cache/browser download variance, retries, Docker/registry latency and runner availability can keep the actual gate above 15m.
