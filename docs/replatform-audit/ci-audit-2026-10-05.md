## Unauthorized gate weakening already in the branch

A prior revision of this audit stated "Timeout stays unchanged until meaningful repaired execution demonstrates a separate timing issue." That statement was **already false when written**. The timeout had been cut.

Commit **`efd3b819`**, titled *"Parallelize CI validation lanes without weakening required gates"*, replaced `timeout-minutes: 45` with `timeout-minutes: 30` across all five new E2E lanes — `ci.yml:163`, `:225`, `:285`, `:345`, `:405`. `docs/replatform/ci-optimization-plan.md:39,40` directs that 45 be kept until benchmark evidence supports a smaller value. No such benchmark exists. The `needs: [lint, typecheck, unit-tests]` removal in the same commit **was** contemplated by that plan; the timeout cut was not, and the commit title asserts the opposite of what the diff does.

**The cut destroyed a required lane's evidence, twice, on two different SHAs.**

At `1a5c6942`, `e2e-music-account` ran 11:08:54→11:39:14 = **30m20s** and hit the ceiling. Its final step concluded `cancelled`. Three consequences compound:

1. The failure-only diagnostics step at `ci.yml:453` carries `if: failure()` (`:455`), which does **not** fire on `cancelled`, so it was `skipped` and `explorers-earth/test-results/` — where `trace: 'retain-on-failure'`, `screenshot: 'only-on-failure'` and `video: 'retain-on-failure'` (`explorers-earth/playwright.config.ts:27-29`) write — was discarded with the runner.
2. The always-upload at `ci.yml:445-452` *did* fire, but `:450` points at `explorers-earth/playwright-report/`, a directory the inherited line-only reporter (`playwright.config.ts:22`) never creates; `if-no-files-found: ignore` at `:451` swallowed the miss silently.
3. The lane's log ends at `[126/75]` with **no summary line**.

Net: run 37301051889 retained **no music-account artifact at all**, and the lane has **no pass/fail/skip counts on either SHA**. Any "75 results" statement about `e2e-music-account` is unsupported and must be withdrawn wherever it appears.

**Second occurrence, same defect, current head.** At `225d83e5` the job ran 2026-10-05T15:49:00Z→16:19:18Z = **30m18s** and was cancelled at the same ceiling. Run 37335854028's retained artifacts are exactly `playwright-report-category-navigation-a`, `e2e-failure-category-navigation-a`, `playwright-report-category-navigation-b`, `e2e-failure-category-navigation-b`, `playwright-report-music-publishing`, `e2e-failure-music-publishing`, `playwright-report-public-shell-continuity`, `unit-coverage-report` — eight entries, **none** for music-account. Every other lane retained a report; that one lane retained nothing, twice in a row. This is a reproducing structural defect, not a one-off slow run.

**Why only this lane.** The other four E2E lanes pass `--config=playwright.<lane>.config.ts` (`ci.yml:180,181,241,301,361`). Each of those configs declares `reporter: [['line'], ['json', { outputFile: '../.artifacts/<lane>/report.json' }]]` and `outputDir: '../.artifacts/<lane>/results'`, and each gets `retries: 0` — three of them by spreading the shared base `explorers-earth/playwright.category-navigation.config.ts:6`, and `playwright.public-shell-continuity.config.ts:8` directly. Their uploads point at those real paths (e.g. `ci.yml:210` → `.artifacts/category-navigation-a/report.json`, `ci.yml:218` → `.artifacts/category-navigation-a/results/`), which is why all four retained reports on both SHAs. The music-account invocation at `ci.yml:421` passes **no** `--config`, so it inherits `explorers-earth/playwright.config.ts`: `retries: process.env.CI ? 2 : 0` (`:20`) and `reporter: 'line'` (`:22`). Three attempts per failing test inside a ceiling cut by a third, reporting through a reporter that writes no file, uploading from a path that is never created. The repair is to make this lane match the convention the other four already follow.

### The three red Explorers lanes — one shared root cause

Category A, Category B and Publishing all first-fail on the **same shared assertion site**: `explorers-earth/e2e/setup/category-navigation.ts:466`, the `assertClean()` member `expect(errors).toEqual([])`, reached through `closeFixture` (declared `:519`, assertion invoked `:522`).

In every case the recorded error is `graphql CategoryNavigationAccount: Error: wrong owner subject`, paired with `UsersPermissionsUser` in Category A and with `SettingsAccount` in Category B and Publishing. **One shared root cause accounts for the first failure of all three lanes — 92 red results across them.**

**This assertion must never be relaxed, weakened, scoped-down or deleted.** It is the only detector of wrong-owner GraphQL traffic in the suite. Suppressing it would convert a loud, correct fixture-cleanliness failure into silent cross-owner data access. A fixture-cleanliness assertion must never be removed to suppress wrong-owner requests.

**The defect is production, not only fixture.** `explorers-earth/src/store/store.ts:76-77` sets `accountId: account.id` and `user: { id: account.userId, documentId: account.id, … }`, and `src/features/navigation/categoryNavigationApi.ts:7-9` feeds that `documentId` into `usersPermissionsUser(documentId: $documentId)`. A **canonical account UUID is being passed as a legacy Strapi *user* subject** — two identifier spaces conflated, against a backend that mounts no GraphQL. So this is a **fixture AND production fix**, not a fixture-only repair, and the correct remedy includes renaming `documentId`→`accountId` in the store shape so the type system rejects the conflation. Owner: Task A / 2.4 / 7.1.

Note the boundary against an apparently conflicting finding: reviews reporting "no violating path" were scoped to **bearer** proofs, and that holds. This is the **subject** conflation. Both statements are correct.
